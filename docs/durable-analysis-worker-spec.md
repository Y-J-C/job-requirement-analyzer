# 第六阶段规格：持久化分析任务与版本切换

## 目标

把 DeepSeek 分析从 API 进程内后台任务迁移为 PostgreSQL 持久化队列和独立 Worker。API 重启或页面刷新后任务仍可恢复；重新分析期间，旧的已确认结果继续参与汇总，直到用户确认新版本后原子切换。

## 已确认的实现假设

- 当前任务量较低，直接使用 PostgreSQL 队列表，不引入 Redis、Celery 或新的基础设施。
- API 只创建 `pending` 分析版本，独立 Worker 负责领取、执行、重试和落库。
- 每个岗位同一时间最多有一个 `pending` 或 `running` 分析任务。
- `job_postings.active_analysis_run_id` 指向当前生效的已确认版本。
- 新版本处于排队、执行、待审核或失败时，旧活动版本继续参与汇总。
- 用户确认新版本时，在同一事务中切换活动版本，并将旧版本标记为 `superseded`。
- 已生效版本只读；需要修改时重新分析生成新版本，避免已发布汇总被原地改写。
- 供应商请求和内部瞬时错误最多重试三次；模型输出无效、输入过长等确定性错误直接失败。

## 数据与状态

`analysis_runs` 新增：

- `attempt_count`：已经领取执行的次数。
- `max_attempts`：最大执行次数，默认 3。
- `available_at`：下次允许领取时间。
- `lease_expires_at`：运行租约到期时间，用于恢复崩溃任务。
- `worker_id`：当前领取任务的 Worker 标识。

`job_postings` 新增：

- `active_analysis_run_id`：当前已确认且对汇总生效的分析版本，可为空。

数据库增加部分唯一索引，约束同一岗位最多一个 `pending`/`running` 任务。已有已确认数据在迁移时回填到各岗位最新的已确认分析版本。

## 执行流程

1. `POST /jobs/{id}/analyze` 锁定岗位、检查状态、创建递增版本并返回 `202 pending`。
2. Worker 使用 `FOR UPDATE SKIP LOCKED` 领取最早可执行任务，设置租约并将岗位标记为 `analyzing`。
3. Worker 调用 DeepSeek；成功后写入未确认要求，将版本设为 `succeeded`、岗位设为 `review_required`。
4. 瞬时失败且仍有次数时，任务重新进入 `pending` 并延迟可用；最终失败时记录稳定错误码。
5. Worker 启动和轮询时回收租约过期的 `running` 任务。
6. 页面通过岗位的最新分析任务接口恢复轮询，刷新不会丢失进度。
7. 人工确认新版本后才切换 `active_analysis_run_id`；汇总始终只读取活动版本。

## API 与界面边界

- 新增 `GET /jobs/{job_id}/analysis-runs/latest`。
- 分析任务响应公开尝试次数和可执行时间，便于诊断，但不公开 Worker 标识。
- 已确认且没有待审核新版本时，审核页面展示活动版本为只读，并提供“重新分析”。
- 有新版本待审核时，仅新版本可编辑和确认。
- 排队、执行和失败期间仍展示活动版本，但保持只读。

## 验收标准

- API 请求返回后，即使未在 API 进程内执行，任务仍保留为 `pending`。
- 独立 Worker 可领取并完成任务；并发领取不会重复执行同一任务。
- Worker 中断后，租约到期任务可恢复；瞬时错误按上限重试。
- 页面刷新后能找到最新任务并继续展示进度。
- 重新分析期间旧汇总不消失；确认新版本后汇总一次性切换。
- 已生效版本的新增、编辑和删除请求返回冲突，不发生原地修改。
- 单元测试、前端测试、代码检查、生产构建和 PostgreSQL 迁移验证通过。

## 本阶段不包含

- Redis/Celery、任务取消、优先级队列和管理后台。
- 文件上传、OCR、登录、多用户权限与生产部署。
